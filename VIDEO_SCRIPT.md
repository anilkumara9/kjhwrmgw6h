## Part 1 — Client pitch (target 4:30, max 5:00)

*Audience: the utility's day-ahead buying team. Goal: impress; lead with money-relevant findings.*

| Time | On screen | Say (script) |
|---|---|---|
| 0:00–0:30 | App Overview, hero + KPI cards | "Every day your desk commits to power purchases a day ahead, based on a wind forecast. We built the tool that shows you exactly which forecast you had at the moment of decision — and, for January 2026, how accurate it honestly was." |
| 0:30–1:30 | KPI cards close-up | "Headline: grading only the forecast available before the 09:50 day-ahead gate, January's average hourly error was about 2,100 megawatts. The critical number is bias: plus 1,840 megawatts. The forecast systematically promised wind that didn't arrive — in 84% of all hours. That's not bad luck; that's a planning assumption you can correct for." |
| 1:30–2:20 | "Look-ahead trap" panel | "A warning about flattering numbers: if you grade the latest forecast ever published — including ones issued during the delivery day — error appears to drop to about 1,770 megawatts. That improvement is an illusion. Those forecasts didn't exist when you had to buy. Our tool keeps decision-time accuracy and this leaky number strictly separate, everywhere." |
| 2:20–3:20 | Daily MAE chart → click worst day (28 Jan) → Day Explorer chart | "Error isn't uniform. On 28 January the miss averaged over 5,300 megawatts. Here's the day: amber is the forecast you traded on, teal is what actually generated. Every hour amber sits above teal is wind you planned around that never arrived — replacement power bought at short notice." |
| 3:20–4:00 | Day Explorer hourly table | "For every hour you can see the forecast value, exactly when it was published, its lead time, and the error in megawatts and percent. Full auditability — no number in this app lacks a source timestamp." |
| 4:00–4:30 | Cutoff selector → switch to 17:30 intraday | "And you can stress-test the decision itself: moving the deadline to the 17:30 intraday gate improves accuracy to about 1,980 megawatts — quantifying what later information is worth. Thank you — we're ready to pilot this with your desk." |

## Part 2 — Technical-lead walkthrough (target 4:45, max 5:00)

*Audience: internal tech lead. Goal: make review easy; show design, code layout, testing, deployment.*

| Time | On screen | Say (script) |
|---|---|---|
| 0:00–0:45 | README architecture (mermaid) diagram | "Architecture: React + TypeScript + Recharts frontend; FastAPI Python 3.12 backend; only two Elexon datasets — FUELHH for actuals, WINDFOR for forecasts. The backend has three modules with a strict split: elexon.py does I/O, analysis.py is pure functions, main.py is a thin API layer." |
| 0:45–1:45 | `backend/app/analysis.py` — `select_decision_forecasts` | "The heart of the system is the point-in-time rule: per delivery hour, pick the forecast with the greatest publishTime strictly before the deadline — D-1 at the configured cutoff. Strictly-before matters: a run published exactly at the gate is excluded. The latest-ever forecast is computed on a separate field, used only for the leakage comparison, so the two can never contaminate each other." |
| 1:45–2:30 | `hourly_actuals` + alignment note; API calls in terminal (`curl /api/summary`) | "Alignment: WINDFOR is hourly, FUELHH half-hourly, so hourly actuals are the mean of the :00 and :30 half-hours — 744 hours, each with exactly two records. The summary endpoint reproduces the verified January numbers: MAE 2,123, bias +1,840, correlation 0.93." |
| 2:30–3:15 | Forecast Runs view for a day; `list_runs` code | "The runs endpoint exposes every publish run targeting a day with eligibility flags — this is what powers the timeline view and makes the selection auditable rather than a black box." |
| 3:15–4:00 | `backend/tests/test_analysis.py`; run `pytest` | "Testing: the analysis module is pure, so the suite runs offline on synthetic fixtures. The key test proves selection never picks a post-deadline — or exactly-at-deadline — forecast, plus hand-computed metric checks. Eight tests, all green." |
| 4:00–4:45 | Repo tree; `docker-compose.yml`; `vercel.json` + `api/index.py`; DEPLOYMENT.md | "Delivery: docker-compose runs backend on 8000 and the nginx-served frontend on 8080. For Vercel, api/index.py re-exports the FastAPI app as a serverless function and the bundled January snapshot — about 2 MB, generated by scripts/fetch_snapshot.py — is included in the function bundle, so the deployment works with zero live Elexon dependency. The same snapshot is the fallback if a live fetch ever fails. One honest caveat, also in the app: WINDFOR may cover a wider wind scope than FUELHH's transmission-metered wind, which could explain part of the bias — flagged as a follow-up investigation, not asserted as fact." |
